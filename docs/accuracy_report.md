Generated by `src/report.py` from cached results; regenerating it makes no API calls.

## Summary

- **Accuracy:** 99.9% of all extracted fields match the source exactly (2 wrong out of 4,992); 155 of 156 documents were read with every field correct.
- **Problem invoices:** the checks sent all 12 deliberately faulty invoices (wrong totals, wrong tax, missing dates, duplicate numbers) to a person for review.
- **False alarms:** 0 correct invoices were sent to review; 141 of 156 documents passed every check and were approved automatically.
- **Misses:** the model misread 2 of 156 documents; 1 of those got through the checks (doc_0071.png: a value that was wrong but still looked consistent; see section 2).
- **Cost:** about $1.67 per 1,000 invoices on the paid tier, about 3.6 s per invoice.

Results are on clean, computer-generated invoices; real-world accuracy will be lower (see Limitations).

## 2. Review queue

Every document runs through these checks (`src/validate.py`). Any failure sends it to `needs_review` with the reasons; otherwise it is `auto_approved`. A check that cannot run (e.g. no tax printed) is *skipped*: it does not block approval but is listed in the queue's `skipped_rules` column.

| Check | What it catches |
|---|---|
| line_totals | quantity x unit price != line total |
| subtotal | line totals do not add up to the subtotal |
| tax | (subtotal - discount) x rate != tax amount |
| total | subtotal - discount + tax != total |
| required_fields | invoice number, vendor, invoice date, total or currency missing |
| due_date | due date before invoice date |
| future_date | invoice date after today |
| duplicate | same vendor + invoice number already received |
| date_sequence | a higher invoice number with an earlier date than a lower one (same vendor); catches day/month swaps that move a date past its neighbours |

All arithmetic checks allow 0.01 for rounding. Duplicate and sequence checks compare each document with the other invoices in the same batch, in arrival order (doc_id). Scans are checked in a batch where those invoices arrive as scans, so a scan is never compared with its own PDF.

### Extraction errors caught by the checks

The model misread 2 of 156 files (table in section 1). For each one: was it sent to review, and by which check? *Unfixed* is the stored model output, *current* is the pipeline today.

| File | Wrong fields | Checks failed (unfixed) | Checks failed (current) | Note |
|---|---|---|---|---|
| `doc_0071.png` | `invoice_date`, `due_date` | **not caught** | **not caught** |  |
| `doc_0116.pdf` | `discount` | tax, total | total | also a deliberate anomaly (total_mismatch) |

Caught on the unfixed output: **1 of 2**.

**Why `doc_0071.png` was not caught:** the correct invoice date is 2026-01-03; the model read 2026-03-01. The misread date 2026-03-01 still falls between the vendor's neighbouring invoices (QN-2025-0666 on 2025-12-08 and QN-2026-0671 on 2026-06-21), and the due date was misread the same way, so every date check is consistent. No rule can detect this from the extracted data alone. Possible next steps: have the model also return dates exactly as printed and flag ambiguous ones (day <= 12 in a DD/MM or MM/DD layout), or check dates against each vendor's known date format.

## 5. Limitations

- **Synthetic data.** All invoices were generated by `src/generate_invoices.py`: 5 clean layouts, invented vendors, consistent formatting. Real invoices vary far more (handwriting, stamps, multi-page tables, photos taken on phones, unusual layouts), so **real-world accuracy will be lower** than the numbers here. That is exactly why every document goes through the checks and the review queue.
- **Small sample.** 120 invoices / 156 files. One extra error moves document-level accuracy by about 0.6 points; treat the percentages as indicative.
- **Exact match only.** A field that is close but not identical counts as wrong; we do not grade partial correctness. Correctly-empty fields count as correct, which lifts the overall percentage; the per-field table shows where that matters (e.g. `discount`).
- **The checks cannot see everything.** They catch inconsistencies (sums, dates, duplicates), not a value that is wrong but still consistent. A misread date that stays in plausible order, or a misread amount on a line that also misreads its total consistently, passes. The anomalies were designed by us, so recall on real-world problems is untested.
- **Batch-dependent checks.** Duplicate and date-sequence checks only see invoices in the same batch; in production they would query all previously processed invoices.
- **Prices and latency change.** Prices are from the official page on the date above; latency was measured on one run from one location on the free tier.
